安全披露

这一页讲两件事：怎么报告一个安全问题（不把它变成公开 exploit），以及这个项目已知的信任边界（哪些地方编译器不给你保证）。

原文是仓库的 SECURITY.md，这一页是它的导读。

一句话版本

不要为疑似漏洞开公开 issue。 用 私有 advisory 表单。

公开 issue 会被索引、被镜像、被缓存——几分钟之内。一份公开报告可以在补丁存在之前就把修复变成 exploit。

报告渠道

优先级渠道
首选GitHub 私有 advisory——只有你和维护者看得见
备选邮件 15901598712@163.com，写同样的信息，并要求回执确认

报告里要包含什么

项为什么重要
版本——仓库根的 VERSION 文件，或 jhyy --help 的第一行修复先落在最新的 release 上
复现——完整的 .jhyy 源码，或者准确的命令行一行 diff 是「当天修复」和「一周来回提问」的区别
实际 vs 预期发生了什么，应该发生什么
退出码见下面那个坑
来源——发布二进制，还是自举构建两者可能表现不同
影响——攻击者能拿到什么，以及他必须先有什么决定严重性，严重性决定时限

用 harness 或 Python subprocess 取退出码，不要读 MSYS2 bash 的 $?。 bash 把退出码截成 8 位（value & 0xFF），所以 ≥ 256 的期望码要先约减：827 → 59、501 → 245、300 → 44、1000 → 232。很多「退出码不对」其实只是这个。

不需要证明可利用性。 源码级的演示就够了——「这是那个让编译器写出缓冲区边界的 .jhyy 文件」就是一份完整报告。

什么算漏洞

算：

  • 生成代码里的内存安全违规——对于程序自己没有做这些事的程序：编译器发出越界写、读写未初始化内存、破坏栈、算错地址。
  • 编译器内部的内存安全——一个构造好的 .jhyy 源文件（或编译器读到的任何其他输入文件）让编译器自己破坏内存、越界写、或者执行攻击者控制的字节。编译器解析不可信输入，而那个输入不该能接管进程。
  • 通过工具链实现代码执行——让编译器运行用户没打算运行的代码：一个解析到意外文件的 import、一个未经清洗就传给外部程序的参数、一个内容能把构建导向别处的构建目录。
  • 安装器或发布产物里的路径穿越——写到它本该触碰的目录之外。
  • 发布完整性——公布的 SHA256.txt 没覆盖它随包发布的那份产物，或发布产物与 tag 出来的源码产出的东西对不上。

不算：

  • 误用文档里写明的不安全特性——未检查的 slice 下标、声明成错误 C 签名的 extern fn、手写的 asm!、#[naked] 函数。文档写清楚了这些是带刃的工具。
  • 语言层面的缺口——还没有借用检查、没有浮点格式化、Vec<T> 还不是元素泛型。这些记在语言规范的附录 B 和公开的问题台账里，不是漏洞。
  • 在你可控的输入上崩溃，且没有内存安全影响——那是 bug，用 issue 报。（除非这个崩溃可以从你没写的源文件触发。）
  • 生成的程序自己的逻辑有 bug。
  • Windows 安装器里打包的第三方工具链自身的漏洞——报给上游；如果你认为打包这个动作本身引入了它自己的问题，也告诉我们。

支持哪些版本

线支持情况
最新 release有安全修复
更早的 release没有——请升级到最新
main（未发布）尽力而为，修复随下个 release

这一页故意不写版本号：永远只有「最新的那个 release」是被支持的那个。版本事实由下载页承担。

报告之后会发生什么

阶段目标
确认报告已收到7 天
分诊——是不是漏洞、有多严重14 天
严重 / 高危的修复发布CI 一绿就发——没有固定日期，但不会故意压着不发
中危 / 低危的修复发布下一个 release

这些是目标，不是保证——这是一个一人项目，对方还有一份正职。如果超过窗口期没有确认，这本身就是这个流程的缺陷：在同一 thread 里说出来，并且认为这种沉默值得升级。

即使结论是「不是漏洞」，你也会拿到分诊结果——一个有理由的「不」是真实答案，比沉默有用。

公开披露

  • 给维护者一个合理的窗口期再公开。 默认期望是首次报告起 90 天。需要更多时间可以商量，显式延期也可以。
  • 如果修复之前就有缓解措施（比如「别用你不信任的构建去编译不信任的 .jhyy 文件」），它会立刻在 advisory 里公布——不会要求你保密。
  • 署名由你决定，用哪个名字或 handle 都可以；不想署名也行。
  • 已经公开了的，在报告里说一声——这改变披露时间线，不影响它是否会被修。

已知的信任边界

下面这些是从项目现状能确认的事实。它们的用处是让你知道「vulnerable」在这个项目里意味着什么。

边界事实对使用者的含义
安装器与 MSI 未签名没有代码签名Windows SmartScreen 首次运行会拦；供应链信任只能靠手动核对 SHA256——见校验与签名。未签名二进制也更容易被第三方杀软拦
没有 GC，没有托管运行时内存安全靠 arena 的生命周期纪律 + 有限的借用检查不是 Rust 级别的保证。借用检查目前只覆盖「同一作用域内重复 &mut 同一变量」；完整 NLL / Polonius 借用检查、生命周期标注 'a、reborrow、跨函数借用都未实装（规范附录 B）
不可变绑定的写保护未实装编译器不检查取地址的对象是否可变&x 对不可变绑定合法；通过这样的指针写入不报错也不生效
extern fn 的 C 侧参数类型不做检查参数 / 返回类型不做限制声明 extern fn takes(s: MyStruct) -> i32; 能编译通过，而且实际按地址传 struct，与 C ABI 不符。函数实参类型也不检查——f(5) 传给 struct 形参能编译，运行时按 struct 布局读寄存器
生成的代码不带额外加固编译器不插 stack canary，不插 guard page链接器施加什么，你就得到什么
编译器没有沙箱它以你的用户权限运行，解析不可信输入未知来源的 .jhyy 源文件就是不可信输入，和交给任何别的解析器一样
编译器会 shell out 到外部 C 工具链解析顺序：JHY_GCC 环境变量 → env.txt → 内置工具链 → C:\msys64 → PATH → 裸 gcc把这个覆盖指向一个不可信的二进制，等于运行那个二进制。环境变量是信任边界的一部分
jhyy run 会执行刚编出来的程序编译并运行不可信源码 = 运行不可信代码编译器不提供任何隔离
没有网络访问，没有遥测不开 socket，不发送任何东西，不读任何凭据只读工具链路径覆盖和两个调试开关
安装器打包了第三方原生工具链那是它自己的供应链面由每次发布随附的校验和覆盖，不是把一份 vendored 副本放在仓库里

arena 不是「只有 arena 没有 free」：JHYY 的 arena 同时提供 arena_reset（复用内存，块不释放）和 arena_free（整块释放）。别照抄别的语言的 arena 模型。

编译器 bug 还是用户程序 bug？

情形该去哪报
编译器做错了——输出错、崩溃、诊断说不通普通 issue，按贡献指南的复现格式写
你的 .jhyy 程序自己算错了不是编译器 bug。回归套件覆盖的是编译器自身的行为，不等于你的程序没有未定义行为——先按语言规范查语义
语言层面的缺口（没借用检查、没浮点格式化、Vec 不是泛型）规范附录 B 与公开台账里都有记录，不是安全 issue
一个已知限制，你想动手做路线图是公开的，见 FACTS.md § 4；开 issue 说明思路
一个 workaround 应该进台账台账公开维护，docs/internal/workarounds.md，只增不删
安全问题走上面的私有 advisory 通道，不要开公开 issue
第三方工具链的漏洞报给上游；但如果你认为打包方式本身有问题，也告诉我们

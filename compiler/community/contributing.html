构建与测试

宿主是 Windows 10 + MSYS2（C:\msys64\mingw64\bin\bash.exe）。

# 依赖
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-binutils

# 构建（jhyy 编译自己；make 会把自举闭环迭代到不动点）
make all           # → compiler/build/bin/jhyy.exe

# 回归
python regress.py                       # 全量
python regress.py --tests=hello.jhyy    # 单个用例
python regress.py --all                 # 带上受门控的用例

不要用 Git Bash 自带的那个 MinGW gcc——它不支持 PE+ 链接，会在链接阶段失败。 所有门都要从仓库根目录跑：脚本按当前目录解析路径，在子目录里跑会把所有文件报成缺失，看起来像漂移，其实不是。

各道门分别管什么

门它管什么什么时候跑
make（自举闭环）跨代产出的 .s 逐字节相同改了 compiler/src0/*.jhyy 之后
python regress.py每个用例的退出码 / stdout 断言任何行为改动之后
python scripts/dev/audit_test_assertions.py --strict每个用例都有能失败的断言（零信号即红）+ 指令与读点对照改测试之后
bash compiler/tests/bootstrap/artifact_checks.sh19 道产物级断言——失效模式在字节布局里，不在程序返回值里，写 .jhyy 测试抓不到动了 codegen 之后
bash compiler/tests/bootstrap/closure_check.shStage 2 的 .s == Stage 3 的 .s（本地门，不接 CI）改了 src0 之后
python regress.py --fixed-pointN=10 跨代 .il + .s 逐字节相同（本地门）发版级流程
bash compiler/tests/bootstrap/artifact_fresh_check.sh提交进仓的那份 jhyy.exe 与现编产物行为一致改了 src0 之后——否则它会红
python scripts/dev/bump_version.py checkVERSION == 全仓每一处版本串动了版本号或版本串

提交前该跑哪个

你改了什么至少要跑
只改文档 / 只改测试文档要事实核对（限制还在吗？修它的 sprint 发布了吗？），CI 跑事实门；测试要 python regress.py + 断言强度审计
改了 compiler/src0/*.jhyymake + python regress.py + artifact_checks.sh，并更新提交进仓的自举产物；动版本号或发版流程再加 --fixed-point

细节见构建与测试与源码构建与自举。

改动分类与对应门槛

这几类必须先设计、后动手

语言语法 / 语义 · ABI 与内存布局 · 内存模型 · 标准库稳定 API · 错误码语义 · 自举边界。

理由：语言规范 v4.0.0 与 ABI 白皮书 v4.0.0 都是已锁定的契约，附录 B 是已知限制的正式清单，诊断码也在规范里成表——一动就影响所有已发布的程序。

目前还没有明文规定的 RFC 流程。 仓库里没有 RFC 模板、编号规则或评审期——RFC 这个词在仓内只出现在两个互联网标准里（RFC 3629、RFC 4122）。现有的替代物是：锁定中的规范 + 附录 B、docs/plans/v4/ 一格一份 plan（结构固定，含 Goal / Scope / 验收门 / 复核清单 / Risks）、以及 FACTS.md § 4 这份排期真相源。官网的 RFC 流程 一节是这块规则正在补的位置。

在规则补齐之前的实际做法：先开一个 issue 说明动机、范围、对现有代码的影响，等维护者拍板再动手；不要直接改规范文本。落在 docs/plans/v4/ 哪一格、验收门是什么，写在 plan 里。

小改动

issue（说明问题）+ 设计说明 + PR，设计说明自包含在 PR 里——不要让 reviewer 自己去翻 issue。

提交与 PR 规范

以下四条是 CONTRIBUTING.md 的原文要求：

  1. 一个 PR 只做一件事。 描述里需要出现「并且」的时候，它大概是两个 PR。
  2. 门必须跑。 没跑过的门等于没过的门。 PR 上每个 CI job 都得绿——包括 SysV ABI 那道 job：它是唯一能真正执行那六个用例的 runner（windows-latest 会跳过它们），所以它绿了不代表覆盖了它们。
  3. 提交信息里总结这次改动；任何 AI 助手参与了代码编写，都要加 Co-Authored-By trailer。
  4. 动了文档就把事实保持同步。

改编译器源码 = 发版级流程

改 compiler/src0/*.jhyy 的成本比改文档高得多：加一个局部变量就会移位模块级 temp 编号，自举构建随之漂移。于是要：

  • 跑全量回归；
  • 刷新自举锚点（make，它会迭代到不动点并装上新二进制）；
  • 提交新的 compiler/build/bin/jhyy.exe——它是 git 跟踪的产物，CI 的 artifact-fresh 门会拿它跟现编产物对拍，陈旧的会被抓出来。

只改注释是免费的：lexer 在 codegen 之前把注释剥掉，编译器二进制保持逐字节相同。

代码风格

  • .editorconfig：UTF-8 / LF / 末尾换行 / 去尾空格；缩进 4 空格（.jhyy / .c / .h / .py / .sh / .ps1）、2 空格（.md / .json / .yml），Makefile 用 tab。
  • C 侧 -Wall -Wextra 零警告。
  • 一份文档一种语言：对外门面（README.md / CONTRIBUTING.md / CHANGELOG.md）英文，中文门面只有 README.zh-CN.md，仓内 docs/** 中文；同一份文档里不许中英混写。中文只用简体。
  • 两份 README 必须一起改——门面分叉比门面过期更糟。
  • 文档里的路径引用按「相对当前文件」写；改完跑 python scripts/dev/docs_facts_check.py（含断链检查）。

测试分层

回归套件共 299 条，按信号来源分三层：

层判定方式条数
真断言断言写在用例源码里215
harness 判定 · 期望编译错误用例声明 // EXPECT-ERROR: "..."56
harness 判定 · 比对退出码用例声明 // EXPECT: N8
SKIP · 用例主动跳过用例带 // SKIP: 指令6
SKIP · 库模块没有入口点的库模块14

215 + 56 + 8 = 279（可跑），加 6 + 14 = 299（总数）。

测试指令集是固定的一组：EXPECT / EXPECT-ERROR / EXPECT-OUT / XFAIL / SKIP / SETENV，新增用例只用这几个。

断言强度审计会报出零信号用例数——一个不可能失败的测试比没有测试更糟，它什么都没查却报成功。

签名要求与反向移植

  • 签名要求：没有。 仓库没有 DCO、没有 GPG 签名要求，GitHub 侧的 web_commit_signoff_required 也是关的。
  • 反向移植（backport）规则：目前还没有明文规定。 仓库只有一条主线（main），没有 release 分支矩阵，也没有 backport 政策。

提 issue 的格式

两个 issue 模板（Compiler bug report / Feature request），也允许空白 issue。报 bug 时这四样缺一不可：

  1. 最小复现——完整的 .jhyy 源码；
  2. 实际 vs 预期输出，含退出码；
  3. 版本——jhyy --help 的第一行（没有 jhyy --version 这个 flag，它从来没存在过）；
  4. 编译器来源——发布二进制，还是自举构建？

退出码要用 harness 或 Python subprocess 取，不要读 MSYS2 bash 的 $?。 bash 把退出码截成 8 位（value & 0xFF），所以 ≥ 256 的期望码要先约减：827 → 59、501 → 245、300 → 44、1000 → 232。很多「退出码不对」的报告其实只是这个。

标签含义来源

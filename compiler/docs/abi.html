ABI v4.0.0

ABI 原文在仓库里，不在这里。 原文：docs/abis/jhyy-abi-v4.0.0.md

本页是那份 ABI 的导读：目标与调用约定、类型布局、聚合类型传参、链接规则， 以及一份已知偏离与未实装项的摘要。冲突时以仓库原文为准。

ABI 锁在 v4.0.0（2026-10-24 随 v4.0.0 final 一同锁版），与语言规范同代。 工具链版本是另一回事，见参考总览。

目标与调用约定

目标三元组调用约定运行时状态
amd64_win（默认）MS x64hosted（链 C 运行时）stable
amd64_sysvSysV AMD64hostedstable
amd64_win_freestandingMS x64freestandingbeta
amd64_sysv_freestandingSysV AMD64freestandingbeta
  • 架构只有 x86-64。 aarch64 / riscv64 未实装（ABI § 12.10）。
  • 四个目标全部走自托管 amd64 后端，没有 QBE 回退路径。
  • amd64_win 与 amd64_win_freestanding 的调用约定逐字节相同； amd64_sysv 与 amd64_sysv_freestanding 同理。

MS x64（amd64_win / amd64_win_freestanding）

规则内容
整型 / 指针参数前 4 个走 RCX RDX R8 R9，其余走栈
浮点参数前 4 个走 XMM0–XMM3，其余走栈
返回值整型 / 指针 → RAX；浮点 → XMM0
Shadow space调用者在栈上预留 32 字节
栈对齐call 前 16 字节对齐

整数与浮点实参共享同一个位置计数器——这是 MS x64 的核心规则：

槽位整数寄存器浮点寄存器
1RCXXMM0
2RDXXMM1
3R8XMM2
4R9XMM3
≥ 5栈栈

⇒ fn f(a: f64, b: i32) 里 a 在 XMM0、b 在 EDX（不是 ECX）。

SysV AMD64（amd64_sysv / amd64_sysv_freestanding）

规则内容
整型 / 指针参数前 6 个走 RDI RSI RDX RCX R8 R9，其余走栈
浮点参数前 8 个走 XMM0–XMM7，其余走栈
Shadow space无
栈对齐call 前 16 字节对齐

整数与浮点是两个独立 bank——整数按出现顺序占 rdi/rsi/…， 浮点按出现顺序占 xmm0–xmm7，各自编号、互不影响。 这与 MS x64 的共享计数器正好相反：同一个 fn f(a: f64, b: i32)， 在 SysV 下 b 落在 RDI。

写混合 int / float 参数的函数时，这条差异是最容易出错的地方—— 纯 JHYY 代码跨目标行为一致（返回值规则相同），但手写汇编对接时会踩。

类型布局

类型sizeofalignof备注

i16 / u1622同上

fn(...) 函数指针88⚠️ 类型位置不认这个语法（语言规范附录 B）
[*]T 切片168{ data: *T @0, len: i64 @8 }

PhantomData<T>01ZST，不占 struct 槽位
  • 有符号整数溢出是定义行为：二进制补码环绕，无运行时检查。
  • 没有独立的 char 类型——字符字面量的类型是 i32，值是 Unicode codepoint。
  • struct 按声明顺序排列、自然对齐；嵌套 struct 内联展开为单层布局。
  • enum 的 tag 是 i32，offset 0；payload 从 align_up(4, max_payload_align) 开始。
  • ⚠️ alignof(enum) 硬编码返回 4，与 enum 布局算出的自然对齐不一致（ABI § 12.2）。

聚合类型传参

Win

参数类型传递方式
struct调用者在栈上建副本，逐字段复制（含嵌套 struct 递归），传副本地址（一个 l 参数）
enum传一个 l（enum 值自身槽的地址），不建副本
[T; N]传一个 l（数组自身地址），不建副本（实质按引用）
[*]T 切片16 字节槽 {data, len}，但只传一个 l 指针指向该槽

⚠️ 只有 struct 真正建副本。 enum / [T; N] / 切片是按地址传递—— 所以在 callee 里改数组会改到调用方的数组。

SysV

条件传递方式
sizeof ≤ 16按 eightbyte 切分分类（INTEGER / SSE），最多 2 个 eightbyte 进寄存器
sizeof > 16MEMORY class —— 整体落在栈上

返回值

返回类型约定
整型 / 指针 / &TRAX
f32 / f64XMM0
struct / enum隐式 sret：调用者分配返回槽，作为隐藏的第 0 个参数在寄存器里传入（Win %rcx / SysV %rdi）
[T; N]⚠️ 不走 sret：callee 自建 16 字节槽，RAX 返回其地址
()无返回值，函数尾部裸 ret

名称修饰

情形符号形式
普通函数<name>
模块内函数<mod>__<name>（调用侧写 mod::fn()）
泛型实例<Base>$<T1>$<T2>（例如 max$i32）
模块内泛型实例<mod>__<Base>$<T1>$<T2>（模块前缀优先）
闭包__closure_<N>（合成名，N 每次编译单调递增 ⇒ 产物可复现）
extern fn原样，不加前缀、不加修饰

泛型修饰名由 parser 按源码顺序拼出，不含指针地址或哈希 ⇒ 确定性。 无重载支持。

程序入口与链接

这一节是最容易搞错的地方。

模式入口符号说明
hostedmain_jhyyC 运行时的 main 调用 main_jhyy(argc, argv)，其返回值作为进程退出码
#[no_std]main链接行 -nostartfiles -nodefaultlibs -Wl,--entry=main -lgcc
  • #[no_std] 不链接 C 运行时启动文件；-lgcc 只提供 ___chkstk_ms 这类编译器内建。
  • #[no_std] 模式下 fn main 必须存在，否则编译错误： error: #[no_std] module must define 'fn main()'。

freestanding 不切换链接方式

⚠️ 两个 freestanding 目标只切换「调用约定归属 + 入口钩子」，不切换链接方式。

链接行是按源文件里有没有 #[no_std] 分支的，跟 --target 无关。

源文件里有 #[no_std] 吗链接行
没有链 runtime.o + helpers.o（C 运行时 bridge）+ Windows 系统库 + -lm
有不链上面两个，改加 -nostartfiles -nodefaultlibs -Wl,--entry=main -lgcc

也就是说：--target=amd64_win_freestanding 本身不会让你不链 C 运行时。 要得到纯 freestanding 产物，源文件里还得写 #[no_std]。

两条分支都带 -g0 -Wl,--build-id=none -Wl,--stack,67108864 … -lm -lkernel32 -luser32 -lshell32 -ladvapi32 —— Windows 系统库与 -lm 是无条件加的（#[no_std] 也加）。 真正的 UEFI / 裸机镜像需要自行用 lld-link（/SUBSYSTEM:EFI_APPLICATION /ENTRY:efi_main） 或自定义链接行完成。

目标 → ABI → 链接方式

目标ABI（调用约定）入口符号链接方式
amd64_winMS x64main_jhyyhosted：链 C 运行时 + Windows 系统库
amd64_sysvSysV AMD64main_jhyyhosted（同上；跨目标必须 --no-link）
amd64_win_freestandingMS x64（与 amd64_win 逐字节相同）用户自备（efi_main / _start）取决于源文件有没有 #[no_std]，不是取决于 --target
amd64_sysv_freestandingSysV AMD64（与 amd64_sysv 逐字节相同）用户自备（efi_main / _start）同上

⚠️ 输出容器格式不由 --target 决定，而由宿主工具链的 ld 决定 （link_with_gcc 没有 target 参数）。各目标的 PE / ELF 产出只是惯例（ABI § 12.9）。

推论：除 amd64_win 外的目标都只能 --no-link，拿 .s 去用与目标匹配的工具链链接。

FFI

方向支持的参数 / 返回类型
JHYY → C全部基础类型、*T、bool
C → JHYY同上
  • extern fn 只声明、不生成函数体，链接期由 ld 解析符号。
  • 不支持：struct / enum 按值跨 FFI 边界、变参函数（JHYY 侧需逐参数列出）、回调函数。
  • ⚠️ extern fn 的参数 / 返回类型不做编译期限制——声明 struct 参数能编译通过， 但实际按地址传，与 C ABI 不符（静默不符，无报错）。
  • 字符串字面量是 UTF-8 字节序列，存放在 .data 段，以 NUL 结尾，作为 *u8 传给 C， 兼容 C 的 char*。

已知偏离与未实装项

ABI § 12 是有意记录、有门或已登记的事实，不是遗漏。

§ 12 的表只列当前仍未闭合的项——已修复的偏离会从表里移除，编号随之前移 ⇒ 引用时请以条目内容而非编号为准。摘要：

#项性质
12.1struct / enum 返回值在所有目标无条件走 sret，无大小阈值——SysV 标准应把 ≤16 字节聚合类型放进 RAX:RDX / XMM0:XMM1偏离 SysV
12.2alignof(enum) 硬编码返回 4，与 enum 布局计算用的 max(4, max_payload_align) 不一致内部不一致
12.3SysV 的非 struct 标量参数仍借 Win 分类器决定 IR 字母——当前不出错，但是隐式依赖隐患
12.4SysV 下 MEMORY class 参数与寄存器溢出参数混排 → 编译期报错；部分合法 SysV 用法当前无法编译能力边界
12.5sret 槽大小 max(4, sizeof(T)) 与 enum 拷贝按 total_size 写入——理论边界，实测恒等理论边界
12.6栈槽只保证 8 字节对齐；当前无 16 字节对齐类型，未触发能力边界
12.7全 spill，只保存 RBP，栈帧显著偏大，依赖 64 MB 栈预留补偿实现特征
12.8UEFI EFIAPI wrapper 未实装：freestanding 的两个钩子（emit_entry_point / no_crt_init）都是空实现——编译器不生成 EFIAPI wrapper，也不自动抑制 CRT / runtime 链接。entry 符号由用户自行提供未实装
12.9无交叉编译容器后端：--target 不切换 PE / ELF 产出能力边界
12.10无 aarch64 / riscv64；.jhyynb 原生二进制格式仍是设计稿，未实装未实装
12.11SysV eightbyte 宽度规则只对第 0 个 eightbyte 成立——第 1 个及以后恒为 8 字节偏离 SysV
12.12SysV 溢出的 f64 栈参缺 16 字节对齐偏离 SysV
12.14Windows 控制台 UTF-8 由运行时设置：runtime.c 的 main 在 stdout 是控制台时调 SetConsoleOutputCP(CP_UTF8) + SetConsoleCP(CP_UTF8)；管道 / 重定向时不动代码页实现特征

§ 12.14 是这一组里唯一用户能直接看见的一条：默认 OEM 代码页在中文 Windows 上是 CP936 / GBK，程序 printf 出去的 UTF-8 字节会被按 GBK 解释 ⇒ 屏幕全是乱码。 运行时只在 stdout 是控制台时才切代码页，正是为了避开这个坑。

§ 12.8 是当前最大的缺口：freestanding 目标标着 beta 不是因为约定没定， 而是因为入口路径还没接上。用户得自己提供 efi_main 或 _start。

稳定性承诺

ABI § 9 明确分成两栏：

此版本锁定（不因 minor / patch 改变）可能在后续版本改变
基础类型的 sizeof / alignofstruct / enum 返回值在 SysV 上的 sret 处理
指针宽度（64 位）alignof(enum) 的取值
struct 字段对齐与排列算法名称修饰方案（引入类型编码 / 重载编码）
enum 的 tag（i32，offset 0）布局SysV 分类器对非 struct 标量的处理
四个目标的调用约定归属（哪个目标用哪套约定）栈槽对齐粒度
名称修饰方案的基本形状（<mod>__<name> / <Base>$<T>）

02 / spike 已经实测到的四件事

不是设计， 是跑出来的。

spike/boot.s 的头注释里列的就是这个 spike 要验证的四件事。下面每一屏都是那个文件里的原话。

boot.s
spike/boot.s 
# UEFI x64 boot path spike -- simplified (ConOut only)
#
# Verifies P0-1:
#   - UEFI x64 hands off in long mode (no mode switching asm needed)
#   - EFI calling convention is MS x64: RCX = first arg, RDX = SystemTable at entry
#   - ConOut function pointers work via [protocol + offset]
#   - isa-debug-exit at port 0xf4 propagates to QEMU exit code
efi_main:
    # UEFI x64 entry convention:
    #   RCX = EFI_HANDLE ImageHandle
    #   RDX = EFI_SYSTEM_TABLE *SystemTable
    push    rbp
    mov     rbp, rsp
    push    rbx
    push    r12
    sub     rsp, 48

    mov     r12, rdx                   # r12 = ST
# CRITICAL: ST offset for ConOut is +64, NOT +80 (+80 is StdErr, see comment below).
# StdErr in OVMF's ConSplitter is NOT registered for the graphics console, so writing
# to it reaches serial but is invisible on the GOP framebuffer.

    # Load ConOut protocol from ST (correct offset is 64, not 80)
    mov     rax, [r12 + 64]            # ConOut (NOT StdErr at 80)
    test    rax, rax
    jz      .Lskip_all
    mov     r13, rax                   # r13 = ConOut (preserve across calls)
    # Hang loop (so GUI stays up long enough to see HELLO/OK).
    # Close QEMU window manually when done viewing.
    # (For automated verification, replace with `out 0xf4, al`.)
.Lhang:
    hlt
    jmp     .Lhang

spike 里做的事其实只有三步，全是对着 ConOut 协议打函数指针：ClearScreen（偏移 48，先擦掉 TianoCore 的启动画面）、 SetAttribute（偏移 40，白字亮红底 0xCF）、OutputString（偏移 8，打 HELLO 和 OK）。 头注释把这个 spike 标成 P0-1 —— 它是 OS 线的第一个待验证点，不是产品的一小块。

一条诚实补充：第四条在代码里留了位置但没接上 —— 当前提交的 boot.s 最后是一个 hlt 死循环， 屏幕上打出 HELLO / OK 给人看，注释里写明「自动化验证时把它换成 out 0xf4, al」。也就是说这条提交走的是给人看的那条路。

◆ 一条重要的区分

「spike」不是「产品的一小块」

头注释把这个 spike 标成 P0-1：它是 OS 线的第一个待验证点，验证的是「能不能启动」这件事本身。把一个 94 行的引导程序读成「内核已经开工了」—— 那是误读。

04 / 方向

方向， 不是已冻结的方案。

跨项目的设计基线现在单点落在编译器仓的 《JHYY OS 侧设计终版》里 —— OS 仓自己还没有对应的设计文档。

能力微内核 + Cap<T>

设计终版把内核身份锁定成「能力微内核（长期）+ 特权分层（首版）」。理由是三份规范（语言规范 v4.0.0 / ABI v4.0.0 / 二进制格式 v1.0.0）已经提供对象分类 type_tag、cap 授权 rights / depth、IPC 原地 cap 传输这套完整授权链条 —— 走传统混合内核，这套二进制格式会退化成装饰。

  • ·能力微内核（长期）
  • ·特权分层（首版）
  • ·Cap<T> 未实装

lang-debug ABI

语言规范 § 19 的「Debug ABI」是跨项目契约：尺寸定案、jhyy 侧的类型表达、编译器不生成 DWARF debug info、FFI 边界提醒。

  • ·§ 19 · 跨项目契约
  • ·不生成 DWARF
  • ·已锁定

GUI

对象骨架（compositor / surface / seat / buffer）足以搭一条双缓冲显示管线，但完整的桌面还没被规范定义。

  • ·4 个对象
  • ·双缓冲够用
  • ·桌面未定义

这些是方向，不是已冻结的实现方案。那份设计终版同时把该由首次架构冻结回答的问题列了出来 —— 线程与地址空间是否分离、内核对象是否统一 header、revoke 是否同步、中断是不是 capability、page fault 归内核还是用户 pager…… 它们现在都还没有答案。.jhyynb 这个 capability 启动格式本身也还是设计稿、未实装。

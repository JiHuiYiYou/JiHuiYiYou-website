01 / Four panels

One workbench, four ways to look.

Writing code, dragging blocks, talking to the model, reading diagnostics — four jobs, four panes. They look like four tools, but they share one AST and one real compiler.

Text view

CodeMirror 6 — just write code. Syntax highlighting, bracket matching, auto-close, indentation, completion (keywords, types, 8 standard library modules), and hover hints that give you the spec section number. Files open in tabs, and opening a second one does not evict the first; the little black dot is computed from content, so it disappears on its own once you undo back to the last saved version.

  • ·CodeMirror 6
  • ·Hover gives spec sections
  • ·Completion for 8 modules

Block view

Blockly 13, drag blocks to write programs. The first screen of the toolbox is "Getting started": functions, print, call, number/string, variables, return — plus ready-made C function declaration blocks (printf / puts / malloc / free / exit, with the parameter list filled in for you) — so the first line of every JHYY program no longer has to be typed by hand through the "raw code" escape hatch.

  • ·Blockly 13
  • ·Owns the whole editing area
  • ·Ready-made C declarations

Claude Code

An embedded chat panel in the right sidebar, driving the already-installed claude CLI on your machine (streaming mode over stdin, with the multi-turn context kept). Claude is wired to the jhyy MCP server, so it can call jhyy_check and get diagnostics from the real compiler instead of guessing. The sidebar also has a "read-only" switch; when it is on, the system prompt states explicitly that the user has asked you not to modify any files.

  • ·Drives your local claude CLI
  • ·jhyy MCP server
  • ·Read-only switch

Bottom panel

A pane that is collapsed by default: "Check" jumps to the Problems page, "Run" jumps to the Terminal page. The terminal is a real shell (MSYS2 bash by default; PowerShell and cmd can be selected) and prefers a real PTY; when node-pty cannot be installed it falls back to pipes, and then full-screen TUIs like vim and top do not run — and when it falls back the status bar shows a badge, so it never silently turns fake.

  • ·Problems + Terminal
  • ·Real PTY first
  • ·Badge on fallback
02 / One AST, two projections

The most convincing one: blocks and text share one tree.

Not two code generators kept in sync — two projections of the same tree.

01 Blocks → text

Change a block, the text follows.

The IDE regenerates the whole source and replaces the text view; the cursor is mapped back to its old position by longest common prefix / suffix — you never watch the cursor jump somewhere else for no reason.

edit block → text follows
02 Text → blocks

Change text, rebuilt on switch back.

Rebuilding the blocks on every keystroke makes the canvas shake too much to use — so the IDE does not rebuild while you type; it rebuilds when you switch back to the block view. The round trip between the two views is lossless.

03 Exclusive

Blocks and text never share the screen.

The block canvas fills the whole editing area and the code editor disappears entirely — switch with the block button in the title bar, Ctrl+Shift+B, or the command palette. Both sides keep their state across the switch: the canvas keeps its zoom and pan, and the editor keeps its undo history and cursor position.

04 Opaque block

Syntax blocks cannot express does not silently disappear.

Generics, turbofish, closures, pointers, borrows, slices, defer, asm!, attributes — these land in an opaque block that holds the original source text. You can move it, delete it; as long as you do not touch it, that part of the code round-trips byte-for-byte without loss.

03 / Status and boundaries

What works, what does not.

Both sides belong on this screen — telling only the good half is the same as telling nothing.

✓ Holds today

The referee is always the real compiler

The IDE never guesses whether a program is right; it runs jhyy.exe, parses its file:line:col: error: … output and shows you the compiler's own diagnostics. The menu bar, the command palette and the keyboard shortcuts are three views of one command table, so a shortcut shown in the menu is always one that really works.

✗ Not yet

The boundaries are on the table

Only Windows x64 is built and verified; Linux / macOS are not built. The IDE does not contain a compiler — every compile and every diagnostic comes from a jhyy.exe you installed yourself (search order: the path configured in the IDE's settings → the environment variable JHY_EXE → the development build in the sibling repo → the official install → PATH). The installer has no code signature, so Windows SmartScreen will stop you once.

→ In flight

The source tree is ahead of every release

The top of CHANGELOG.md still has an "Unreleased" section (the terminal rework, the settings dialog, and so on) — the source tree is ahead of every released version.

◆ One important distinction

What "one shared AST" actually proves

Two views sharing one AST proves one single source of truth — they are two projections of the same tree. It does not prove that blocks can express every piece of syntax: what they cannot lands in an opaque block holding the original source, and that part is still editable only in the text view.

04 / Numbers

What the IDE claims does not count.

The IDE's parser and printer must say the same thing as the real compiler. That is guaranteed by the compiler repo's own example programs — the corpus is the compiler repo's compiler/tests/examples/, and it grows together with the compiler.

02 / The four things the spike has measured

Not a design, a measurement.

The header comment of spike/boot.s lists the four things this spike is meant to verify. Every panel below is that file's own words.

boot.s
spike/boot.s 
# UEFI x64 boot path spike -- simplified (ConOut only)
#
# Verifies P0-1:
#   - UEFI x64 hands off in long mode (no mode switching asm needed)
#   - EFI calling convention is MS x64: RCX = first arg, RDX = SystemTable at entry
#   - ConOut function pointers work via [protocol + offset]
#   - isa-debug-exit at port 0xf4 propagates to QEMU exit code
efi_main:
    # UEFI x64 entry convention:
    #   RCX = EFI_HANDLE ImageHandle
    #   RDX = EFI_SYSTEM_TABLE *SystemTable
    push    rbp
    mov     rbp, rsp
    push    rbx
    push    r12
    sub     rsp, 48

    mov     r12, rdx                   # r12 = ST
# CRITICAL: ST offset for ConOut is +64, NOT +80 (+80 is StdErr, see comment below).
# StdErr in OVMF's ConSplitter is NOT registered for the graphics console, so writing
# to it reaches serial but is invisible on the GOP framebuffer.

    # Load ConOut protocol from ST (correct offset is 64, not 80)
    mov     rax, [r12 + 64]            # ConOut (NOT StdErr at 80)
    test    rax, rax
    jz      .Lskip_all
    mov     r13, rax                   # r13 = ConOut (preserve across calls)
    # Hang loop (so GUI stays up long enough to see HELLO/OK).
    # Close QEMU window manually when done viewing.
    # (For automated verification, replace with `out 0xf4, al`.)
.Lhang:
    hlt
    jmp     .Lhang

What the spike actually does is three steps, all of them calls through the ConOut protocol's function pointers: ClearScreen (offset 48, which first wipes TianoCore's boot splash), SetAttribute (offset 40, white text on bright red background 0xCF), OutputString (offset 8, prints HELLO and OK). The header comment marks this spike as P0-1 — it is the first point to verify on the OS line, not a small piece of a product.

One honest note: the fourth point has a place in the code but is not wired up — the boot.s in the current commit ends in an hlt infinite loop, printing HELLO / OK for a human to look at, and the comment says to replace it with out 0xf4, al for automated verification. In other words, this commit takes the human-facing path.

03 / Status and boundaries

What it is today, what it is not.

Both sides belong on this screen — telling only the good half is the same as telling nothing.

✓ Holds today

It boots, and it measured four things

BOOTX64.EFI runs on UEFI x64 and prints HELLO / OK on screen. The build is one gcc command, and the source behind it is those 94 lines of boot.s.

✗ Not yet

No kernel, and no release channel

The repo has only one directory, spike/. The design documents have been cleared for a rebuild; the roadmap is still to be rewritten. There is nothing to install or run, and no release channel of any kind.

→ Scheduled later

Sixteen version slots, none of them started

The whole OS line — OS-1 … OS-16 in the compiler repo's docs/internal/FACTS.md § 4.3 — is planned for the compiler's v4.6 → v4.15.

◆ One important distinction

A "spike" is not "a small piece of the product"

The header comment marks this spike as P0-1: it is the first point to verify on the OS line, and what it verifies is "can it boot?" itself. Reading a 94-line bootloader as "the kernel has started" is a misreading.

04 / Direction

Direction, not a frozen plan.

The cross-project design baseline now lives in a single place — the compiler repo's "JHYY OS-side design, final version" — the OS repo itself has no matching design document yet.

Capability microkernel + Cap<T>

The final version locks the kernel identity to "capability microkernel (long term) + privilege layering (first version)". The reason is that the three specs (language spec v4.0.0 / ABI v4.0.0 / binary format v1.0.0) already provide a complete authorization chain: object classification type_tag, cap authorization rights / depth, in-place cap transfer over IPC — going with a traditional hybrid kernel would turn that binary format into decoration.

  • ·Capability microkernel (long term)
  • ·Privilege layering (first version)
  • ·Cap<T> not implemented

lang-debug ABI

The "Debug ABI" in language spec § 19 is a cross-project contract: settled sizes, the type representation on the jhyy side, the compiler emitting no DWARF debug info, and FFI boundary reminders.

  • ·§ 19 · cross-project contract
  • ·No DWARF
  • ·Locked

GUI

The object skeleton (compositor / surface / seat / buffer) is enough to build a double-buffered display pipeline, but a complete desktop has not been specified.

  • ·4 objects
  • ·Double buffering is enough
  • ·Desktop unspecified

These are direction, not a frozen implementation plan. That final version also lists the questions the first architecture freeze should answer — whether threads and address spaces are separated, whether kernel objects share a uniform header, whether revoke is synchronous, whether interrupts are capabilities, whether a page fault belongs to the kernel or to a user pager… They do not have answers yet. The .jhyynb capability launch format itself is still a design draft, not implemented.

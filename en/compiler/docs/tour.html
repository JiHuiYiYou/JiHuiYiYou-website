Language Tour

This is a tour, not the spec. The language spec is the authority — it is locked, and the known limitations are collected in its appendix B: spec.

The overall shape of the language

Statically typed. Expression-oriented. Compiled to native code.

type Point = struct { x: i32, y: i32 }

fn dist_sq(a: Point, b: Point) -> i32 {
    let dx = a.x - b.x;
    let dy = a.y - b.y;
    dx * dx + dy * dy
}

fn classify(n: i32) -> *u8 {
    match n {
        0        => "zero",
        1..10    => "single digit",
        10 | 20  => "round number",
        _        => "other",
    }
}

extern fn printf(fmt: *u8, val: i32) -> i32;

fn main_jhyy() -> i32 {
    let p = Point { x: 3, y: 4 };
    let q = Point { x: 0, y: 0 };
    printf("d² = %d\n", dist_sq(p, q));
    printf("%s\n", classify(42));
    0
}

Three things are worth noting:

  • A function body is an expression — the last expression is the return value.
  • if, match and blocks are values themselves, not just statements.
  • A string literal is a *u8 (NUL-terminated UTF-8 bytes in the .data section); no conversion is needed.

Four capabilities that are most often misread

CapabilityStatusWhat it actually means
[*]T (slice)AvailableIt is a view over an array — writes go back to the original array, and indexing is not bounds-checked
PhantomData<T>Type level onlyLegal as a struct field; but instantiating it is a compile error
asm!RestrictedIt must be a string literal — no operand constraints, no clobbers; AT&T syntax, x86-64 only
Cap<T>Layout onlyThe 8-byte layout is fixed and testable, but you cannot construct a value yet — real capability semantics are on the roadmap

Modules and the standard library

import pulls in a module. There is no std:: prefix — import std::vec; is a compile error.

import io;

extern fn puts(s: *u8) -> i32;

fn main_jhyy() -> i32 {
    io::std_io_print("hello from the JHYY stdlib\n");
    puts("and from libc, through extern fn");
    0
}
ModuleWhat it provides

Talking to C

extern fn printf(fmt: *u8, val: i32) -> i32;

extern fn calls C functions under the C ABI. Two things to remember:

  • There is no variadic form. Every C argument has to be written out one by one.
  • Argument types are not checked against the C signature. Write it wrong and it still compiles; the problem only shows up at runtime.

For struct layout and calling convention see the ABI whitepaper.

Memory

There is no garbage collection and no RAII. Memory is yours to manage:

  • explicit pointers (*T), and manual allocation through the runtime's arena or your own allocator;
  • if you want, defer for scope-exit cleanup — it runs LIFO (but not on an implicit tail return);
  • the standard library has arena; use it directly where it fits.

This is a deliberate choice: the language targets systems work, where a predictable memory model matters more than convenience.

What is not there yet

Listed honestly — the project is pre-1.0 and says so itself:

You want to…Today
Use generics with traitsNot yet — queued behind the OS line
Use closures that capture variablesNot yet — capturing is a compile error today
Print floating-point numbersNot yet — fmt has no float formatting
Target aarch64 / riscv64Not yet — x86-64 only
Put it into productionNot yet — the spec is still moving

The authoritative list (with versions) is in the repository's FACTS.md; the item-by-item limitations are in appendix B of the spec.

Reference Overview

This page is the index of the "language reference" group. JHYY's reference material comes in three layers, and each layer guarantees something different — read them mixed together and it is easy to confuse "how do you write this language" with "how do two artifacts recognize each other".

The three layers of reference

LayerWhat question it answersWhat it guaranteesVersion nature
Language specSyntax and semanticsWhat a legal program is, what each expression means, which behaviours are definedA locked contract
ABIType layout, calling convention, linking rulesHow the compiler, artifacts and external libraries recognize each otherA locked contract
CLI / standard libraryHow to use the concrete tools and APIsHow the commands are typed, what the functions are called, what they returnFollows the toolchain version

The first two layers are contracts: an implementation must obey them, and only then is it "JHYY". The third layer is usage — it evolves with the toolchain and carries no stability promise.

Contract version ≠ toolchain version

This is the thing people get most easily tangled up in.

Language spec v4.0.0 and ABI v4.0.0 were each locked on 2026-10-24, together with v4.0.0 final. The toolchain is a separate line — the current stable version is v4.1.5 (the version changes; the download page is authoritative).

In other words:

v4.1.x is an evolution of the implementation of the v4.0.0 contract, not a modification of the contract.

A newer compiler may support one more syntactic sugar or fix one more bug, but as long as the spec and the ABI are still v4.0.0, the rules by which artifacts recognize each other have not changed by a single word. Conversely, the day the spec goes to v5.0.0 that is a new contract, and the compatibility of old artifacts has to be assessed separately.

One corollary: which document you should cite while writing code depends on who you need to be recognized by. Recognized by another JHYY artifact → look at ABI v4.0.0. Recognized by a C library → also look at ABI v4.0.0. Just want to know "how to write it" → look at spec v4.0.0.

The docs are not the source of truth — the repository is

This page, this group of references, and the whole site wiki are hand-written companion documentation. Their job is to tell you "which file the fact lives in", not to restate the fact.

The reason is simple: numbers that change (version numbers, regression baselines, the list of limitations) copied into a second document mean that the next day there are two numbers that contradict each other, and the reader has no way to know which one to believe.

So every assertion has to be traceable to a file:

Kind of factWhere it lives
Numbers and schedules that changedocs/internal/FACTS.md
Known limitations and workaroundsdocs/internal/workarounds.md
What each version changedCHANGELOG.md
How the compiler is put togetherdocs/internal/architecture.md

Repository: github.com/JiHuiYiYou/JiHuiYiYou-compiler

If the wiki and the repository disagree — the repository wins, then file an issue so we can fix the page.

One document outside this group

docs/abis/jhyy-binary-format-v1.0.0.md — the design draft of the JHYY native binary format (.jhyynb), not implemented yet (ABI § 12.10). No artifact has implemented it so far, so it carries no compatibility promise at all.

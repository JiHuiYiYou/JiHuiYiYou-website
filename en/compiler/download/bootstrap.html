Build from source and bootstrap

This page explains how to build the compiler from source, and what the "self-hosted closure" actually proves and what it does not prove. The second question matters more than the first.

Build prerequisites

RequirementExplanation
HostWindows x64 — jhyy.exe is a PE executable, and the self-hosted closure has to be able to execute it
MSYS2The build host. This is a requirement of "building the compiler from source"; installing the compiler with the installer does not need MSYS2
mingw-w64-ucrt-x86_64-gccC compiler
mingw-w64-ucrt-x86_64-binutilsas / ld / objdump and the rest
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-binutils

Do not use the MinGW gcc that ships with Git Bash (/c/Program\ Files/Git/mingw64/bin/gcc.exe) — it does not support PE+ linking, and it will get stuck in the linking stage without printing a single character.

[!WARNING] Whichever gcc / ld appears first on PATH is the one that gets used. The Windows runner image ships an old MSYS2 in C:\mingw64 placed ahead of the rest, which is the most common way this goes wrong. Pass the MSYS2 root directory explicitly when building.

Build

git clone https://github.com/JiHuiYiYou/JiHuiYiYou-compiler.git
cd JiHuiYiYou-compiler
make all        # → compiler/build/bin/jhyy.exe（~2 MB）

make now has only two targets:

targetWhat it does
allThe default target: builds runtime.o / helpers.o, runs the self-hosted closure check, and produces jhyy.exe plus its copy jhyy_v1.exe.exe
cleanRemoves the build outputs (keeps jhyy.exe — delete it and the repository is unusable on the spot)

make stage0, make selfhost and make test have all been removed, so don't go looking for them in the old documentation: the C-side compiler was removed wholesale in v4.0.21, and stage0 disappeared with it; selfhost and test were removed on 2026-11-03 — the check the former ran is already guaranteed by make itself (a permanently green gate is noise), and the latter was only ever a shell of an echo "TODO: test runner".

Directory layout

This repository has no stage0 any more. The bootstrap binary is the committed one that already sits in the repository, compiler/build/bin/jhyy.exe — a fresh clone has it, because it is a git-tracked artifact. The compiler compiles compiler/src0/ by itself:

JiHuiYiYou-compiler/
├── compiler/
│   ├── src0/                   compiler sources (the only implementation, 31 modules)
│   │   ├── std/                standard library, 8 modules: mem / fmt / io / math / string / vec / os / arena
│   │   └── codegen_amd64_*.jhyy self-written backend: IL lexer / emit_* / peephole / register cache
│   ├── runtime/runtime.c       C runtime (arena + main entry)
│   ├── src0/jhyy_helpers.c     C bridge: the extern declarations between the compiler and Win32
│   ├── tests/
│   │   ├── examples/           regression cases, 301 in total
│   │   └── bootstrap/          fixed_point.sh · closure_check.sh · artifact_checks.sh · byte_equal*.sh
│   └── build/
│       ├── obj/                prebuilt _jhyy_runtime.o / _jhyy_helpers.o
│       └── bin/                jhyy.exe (the git-tracked anchor) + jhyy_v1.exe.exe (a byte-identical copy regenerated by every make)
├── runtime/linux_elf/          Linux ELF runtime (crt0.S + link.ld)
├── bench/                      benchmark suite
├── regress.py                  regression test suite (repository root)
└── installer/                  WiX installer + bundled ucrt64 toolchain

The double extension of jhyy_v1.exe.exe is not a typo: make regenerates it on every build (it is a byte-identical copy of jhyy.exe), and the local closure gates refer to it by that name.

The self-hosted closure

The jhyy.exe rule of make does three things:

  1. Copies the current (committed) jhyy.exe into _boot_anchor.exe;
  2. _boot_anchor.exe compiles src0/main.jhyy → _boot_new (with the .s), and _boot_new.exe compiles it once more → _boot_new2 (with the .s);
  3. Closure check: cmp -s _boot_new.s _boot_new2.s — the output of the new compiler compiling src0 must be byte-identical to the output of that compiler compiling itself.

The third step is not "compile two generations and compare once", it iterates to a fixed point: if they differ, the anchor is advanced by one generation, at most 3 rounds; in the round that converges, generation N is the fixed point (generation N+1 produces the same artifact), and installing that one is correct. Three rounds without convergence ⇒ hard failure.

The fixed point is run to, not assumed. And this step carries a non-empty guard: comparing two empty files would also be judged "identical", so a compiler that "silently exits 0 but produces no .s" gives a false green — this guard was only added on 2026-11-03.

There is a drift check after that: when src0 / runtime agree with HEAD, the new artifact must be byte-identical to the one committed into the repository, otherwise make fails (STRICT_TOOLCHAIN=1, on by default). CI passes STRICT_TOOLCHAIN=0 — that is not loosening the criterion, it is drawing a line of responsibility: CI does not publish, it verifies the artifact that was committed into the repository; the drift check governs "should this compiler be published", not "can it be built".

Comparing the .s and not the .exe is deliberate: the .s is a function of (source × compiler) and is independent of the host gcc version; the .exe is a function of (source × gcc version), and comparing across toolchains is guaranteed to produce false positives.

Where each of the three closure gates runs

ScriptCriterionWhere it runs
compiler/tests/bootstrap/fixed_point.shCross-generation .il + .s byte-identical at N=10 (plus a cross-generation exit code of 42 for cap_test.jhyy). N=3 is the main gate, N=4..10 are informationalLocal gate: python regress.py --fixed-point
compiler/tests/bootstrap/closure_check.shv2.s == v3.s (Stage 2 and Stage 3 byte-identical)Local gate: bash compiler/tests/bootstrap/closure_check.sh
compiler/tests/bootstrap/artifact_checks.sh21 artifact checks (expected-FAIL model)CI gate: bash compiler/tests/bootstrap/artifact_checks.sh

Neither fixed_point.sh nor closure_check.sh is wired into CI. The former is a release-grade procedure (run it after changing src0), the latter was deleted from CI on 2026-11-03 — the closure in CI is already covered by make itself, and running it again just restates the same conclusion; a permanently green gate is noise. artifact_checks.sh is the CI gate: its 21 artifact checks run in CI.

The value of artifact_checks.sh lies in the fact that the failure modes it verifies are not in the program's return value but in the byte layout of the artifact: a defect like the 1024 cap on the per-fn table passes when written as a .jhyy test case (all results correct, recursion depth unchanged), and only shows up as subq $N, %rsp jumping in the .s from 8368 to 96928.

Determinism ≠ correctness

This is the most important sentence on the page.

What the self-hosted closure proves is "generational determinism": given the same source, the assembly produced by the second generation is byte-identical to the one produced by the first.

It does not prove semantic correctness. A deterministic but wrong compiler closes the loop perfectly — compile + into - and the two generations still agree. This is the classic trusting trust gap.

Semantic correctness is covered by the regression suite: 281 PASS / 0 FAIL / 20 SKIP, 301 in total. The assertion strength audit counts separately 217 real assertions, with 0 zero-signal cases (no case reports a pass without checking anything at all).

python regress.py                       # full regression
python scripts/dev/audit_test_assertions.py --strict   # assertion strength audit

The two gates have a clear division of labour: the closure governs "two compilations of the same source agree", the regression governs "whether the thing that came out behaves correctly". If the first passes and the second does not, the compiler is stably getting the same thing wrong; if the second passes and the first does not, the emit layer is non-deterministic — both cases mean stop.

What a reproducible build has to pin down

The parts that the repository can actually vouch for:

Pinned itemValue / How
TimestampSOURCE_DATE_EPOCH = 1234567890 (nailed down in the Makefile; the compiler also sets it before spawning the linker subprocess)
Debug info-g0 — otherwise the build path that the mingw-w64 CRT pulls in would break the byte-identical comparison
build-id-Wl,--build-id=none — same reason
Compile flagsCFLAGS_REPRO = -std=c11 -Wall -Wextra -g0 -Wl,--build-id=none
Toolchain layoutgcc derives cc1 / collect2 / as / ld from its own location; the toolchain directories must not be flattened, and the ucrt64/ level must not be renamed

Full cross-machine reproducibility is still one step short: the .exe is a function of (source × gcc version), so anything built with a different gcc version is necessarily different. That is why cross-machine comparison has to compare the .s, not the .exe.

On top of that, the repository currently does not ship a "committed-state sha manifest" with the tarball — the archive downloaded from GitHub codeload has no git metadata, the byte-level drift check has nothing to compare against, and make says so explicitly ("skip") instead of pretending to pass.

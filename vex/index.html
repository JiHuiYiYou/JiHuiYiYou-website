01 / 目标硬件

VEX V5 Brain： 一块 Zynq。

ARM，Xilinx Zynq（Cortex-A9 + FPGA），有 VFPv3 + NEON。下面每个数字都出自实测，不是查手册。

SoC Cortex-A9

Xilinx Zynq

Cortex-A9 + FPGA 集成的 SoC，带 VFPv3 + NEON。这是 ARM 态单精度浮点加 SIMD 的那套硬件底子。

规格书 § 4 目标平台 ↗
指令集 定长 4 字节

ARM 态，不是 Thumb

目标是 ARM 态、4 字节定长 ⇒ 后端不必做 Thumb-2 变长编码。⚠️ 但 clang 的 flags 仍写着 -target thumbv7-none-eabi —— 详见第 04 屏。

规格书 § 4 目标平台 ↗
内存 DDR

DDR 基址 0x03800000

链接脚本 lscript.ld 里的 ps7_ddr_0_S_AXI_BASEADDR。堆 1 MB、栈 14 KB —— 递归深度是硬约束。

规格书 § 11 内存预算 ↗
入口 0x03800020

紧跟在 32 字节头后面

产物头 32 字节是 XVX5 + 版本 1，入口紧跟其后在 0x03800020。SDK 的 objcopy 直出最终格式，不需要额外转换器。

02 / 路线 B

换掉的是 clang 的位置， ld 及以下原样不动。

不是「转译成 C++」。但边界要说清。

01 A 路 / B 路

黄金参考 vs 目标。

A 路（第 0 步，黄金参考）：JHYY → C 源码 → clang → .bin。
B 路（目标）：JHYY → ARM 机器码（.o）→ 官方 SDK → .bin。
B 路出的是 ARM .o，然后链官方 SDK 的 lscript.ld / stdlib_0.lib / libv5rt.a，最后 objcopy 出 .bin。

A 路 · clang → B 路 · JHYY 直出
02 同构

跟 pros-rs 当年是一个路子

Rust 出 .o、链 libpros；这里是 JHYY 出 .o、链官方 SDK。区别是带着实测重走，不带它那些沉没成本。

03 推论

三样锁不住，两路就没法对拍

ABI 必须锁死（softfp）、入口必须锁死（符号名 main）、绑定面必须锁死（每个 extern fn 逐字对应一个 C 符号）—— 链哪份库就认哪份 ABI。

04 拦路虎

JHYY 现在没有 ARM 目标。

ABI v4.0.0 把指针宽度锁死 64 位，四个目标全是 amd64；而 V5_DeviceT 是 4 字节的 C 指针。 ⇒ ARM 目标必须先把指针宽度定成 4 字节，不定，连 extern fn 都对不上。这是 B 阶段的第一块硬骨头 —— 写进规格书，免得有人用最贵的方式发现它。

JHYY 指针宽度64 位
VEX 的 C 指针4 字节
JHYY 目标4 个，全 amd64
ABI 锁定softfp
03 / 规格书八件事

缺一不可， 八件全部实测。

事实基线文档是这个项目「会变的数字与平台事实」的唯一真相源。 测量日期 2026-11-08，机器 Windows 10 + MSYS2，测量方式全部是本机实测（编译 / 反汇编 / readelf / nm），零 JHYY 变量。

已实测 01

产物格式与签名布局

SDK 的 objcopy 直出最终格式，头 32 字节是 XVX5 + 版本 1，入口紧跟其后。不需要额外转换器。

已实测 02

vexStartup 替你干了什么

启动链完全闭合：清 .bss → stdlib 版本校验 → newlib impure data → __libc_init_array → vexMain → __libc_fini_array。反汇编 + 重定位双重确认。

已实测 03

符号修饰规则

C++ vex:: 在 libv5rt.a 里有 1404 个 mangled 符号（要 Itanium mangling ⇒ 不碰）；纯 C vex*() 那层 JHYY 的 extern fn 直接绑，零胶水层。

已锁定 04

softfp / hard 的决定

锁定 softfp：我们的 ELF 与 libv5rt.a 都没有 Tag_ABI_VFP_args 标签，按 ARM ABI 缺省即 base standard variant。

已实测 05

struct 传参的 C 对齐

packed 与非 packed 都有。整个纯 C API 里只有一个按值传的 struct（V5_DeviceVisionRgb，≤4 B ⇒ 寄存器传参），其余一律指针传递。

已核实 06

最小绑定面

确切函数名已核实存在，另有一份 JHYY 侧逐字对应的清单（改一处 = 改两路）。入口符号必须是不带修饰的 main。

已实测 07

场控状态从哪读

vexCompetitionStatus / vexCompetitionControl，位含义已静态实测（2026-11-09，不需要硬件）。

已实测 08 · 真机

消息泵 tick 频率

100 Hz（调度 tick = 10 ms），2026-11-09 在真 Brain 上测得 —— 50 次 vexDelay(1) = 500 ms。规格书八项里最后缺的一条，已补上。

04 / 三条坑

原文里被明确警告过的 三件事。

01 工具

MSYS2 自带的 objdump 是 x86-only

对 VEX 产物会报 can't disassemble for architecture UNKNOWN! ⇒ 必须用 arm-none-eabi-objdump（本次是额外装的，binutils 2.47）。readelf 两边都能读。

02 版本

目标说 Thumb，实测产物是 ARM

SDK 的 clang 是 8.0.0，flags 里写着 -target thumbv7-none-eabi，但实测入口处是 ARM 态指令（e59f00a0 是 ARM 态 LDR literal，Thumb-2 会是 f8df）。这个组合依赖具体版本的 codegen 行为 ⇒ 换 clang 版本必须重测，不能把结论直接搬过去。

03 环境

实测环境是 Windows 10 + MSYS2

工具链路径、shell、objcopy 的行为都跟这个环境绑定。换机器重测时，这三条结论要重新确认一遍。

→ 正在做

Day 1–2：emitter 发 C

第一个闭环已通（2026-11-10）：同一个 hello.jhyy，主仓编译器那条路与本仓 emitter 那条路，stdout 逐字相同 + 返回码相同。第一份真 JHYY 程序（vex_demo.jhyy）也编出了 V5 二进制（2516 B），它的绑定面对象与黄金参考逐字节相同 ⇒ JHYY 路与手写 C 路调的是同一个符号。最小子集 + 最小绑定面（先只绑 vexDeviceGetByIndex / vexDeviceMotorVelocitySet / vexDelay / jhyy_vex_display_puts）—— 发 C，不发 C++。下一步：VEX 的 .bin + 真机跑。

◆ 一条重要的区分

Day 3 的「一致」指的是行为，不是字节

A 路和 B 路是两个不同的代码生成器（.s 必然不同，.o 段布局也可能不同）⇒ .s / .o / ELF / .map / .bin 五层产物是各自的诊断证据，不是逐字节比对对象。逐层比对只是为了定位不一致发生在哪一层。

三条纪律：永久旁路 —— 主仓管语言，本仓管 VEX 目标支持；不回推主仓，主仓工作树从不被碰，编译器只读、按 commit 钉住、走影子构建； 第 0 步的产出是知识，不是代码 —— emitter 是探针，不许长成产品； 产物本地留存，不进版本库 —— .bin / ELF 含 libv5rt.a 的代码（VEX 专有），在「SDK 再分发」拍板前不进公开 repo；留存靠本地 + 可复现脚本 + 哈希清单。

先量清楚， 再往前走。

这条线不靠规划靠实测：把 VEX 侧的未知数全部变成数字，剩下的就是照着数字干活。

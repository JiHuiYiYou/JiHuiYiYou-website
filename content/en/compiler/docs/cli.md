`jhyy` has exactly one binary, four subcommands, and two global options. Below is a
behavior table verified item by item — including artifact names and exit codes — plus
three command-line quirks that bite.

---

## 1. Command table

| Command | Purpose | Artifact |
|---|---|---|
| `jhyy compile <file.jhyy> [-o output]` | Compile + link | `<output>.exe`; the intermediate assembly (`<output>` + `.s`) is left on disk too |
| `jhyy build <file.jhyy> [-o base]` | Compile only, **no** link | `<base>.s` |
| `jhyy run <file.jhyy>` | Compile + link + execute | A temporary artifact `<name>_run.exe` (left on disk after the run) |
| `jhyy dump <file.jhyy>` | Parse only, print the AST tree | Printed to stdout |

Without `-o`, the output name is the base name of the input file: `jhyy compile
hello.jhyy` ⇒ `hello.exe`, `jhyy build hello.jhyy` ⇒ `hello.s`.

`-o` is a **base name**; the suffix is appended automatically: `-o foo` ⇒ `foo.s` /
`foo.exe`; `-o foo.s` ⇒ still `foo.s` (it does not become `foo.s.s`), `-o foo.exe` ⇒
`foo.exe` (the assembly next to it is `foo.exe.s`).

## 2. The difference between the three subcommands (key point)

`compile` / `build` / `run` are three cut points on the same pipeline:

```text
.jhyy → lex → parse → sema → IL → self-written amd64 backend → .s → gcc + ld → .exe
                             └── build   = stops at .s
                                        └── compile = goes on through gcc + ld
                                                     └── run = then executes
```

| | `build` | `compile` | `run` |
|---|---|---|---|
| Parse + semantic analysis | yes | yes | yes |
| Produce `.s` | yes | yes | yes |
| Invoke gcc / ld to link | no | yes | yes |
| Execute | no | no | yes |

### Two equivalent paths

```bash
jhyy build   x.jhyy -o out            # ⇒ out.s
jhyy compile --no-link x.jhyy -o out  # ⇒ out.s
```

The `.s` files the two paths produce are **byte-identical** — including the `.section`
directives generated by `#[link_section]` (both paths apply the same section
handling). The repository has an artifact check (`link_section_build`) that pins this
equivalence down.

Measured: for a file that carries both `#[link_section]` and `#[naked]`, `cmp` on the
`.s` files from the two paths is an exact match.

### One place that disagrees with the help text

`jhyy --help` says `compile ... (a lib without main is compiled only)`. Measured:
running `jhyy compile` on a file **without `main_jhyy`** does produce the `.s`, but the
link step still runs and fails (`collect2.exe: error: ld returned 1 exit status`), exit
code 1. ⇒ To get only the assembly, use `jhyy build` or `jhyy compile --no-link`.

## 3. Options

| Option | Effect |
|---|---|
| `--target=<triple>` | Select the target, default `amd64_win`. **Anywhere** (before or after the subcommand); when several are given, **the last one wins** |
| `--no-link` | Produce `.s` only, skip the link step. **Anywhere** (before or after the subcommand) |
| `--help` | Print the full help and exit 0. It can be triggered at **any position** — `jhyy --help` and `jhyy compile --help` print the same thing |

Running `jhyy` with no arguments at all prints the **same** full help.

### The four targets

| Triple | Calling convention | Runtime | Can this build link it |
|---|---|---|---|
| `amd64_win` | MS x64 | hosted (links the C runtime) | yes (the only one it can link) |
| `amd64_sysv` | SysV AMD64 | hosted | no, `--no-link` is required |
| `amd64_win_freestanding` | MS x64 | freestanding (UEFI) | no, `--no-link` is required |
| `amd64_sysv_freestanding` | SysV AMD64 | freestanding | no, `--no-link` is required |

Three things about freestanding:

1. **Freestanding only switches "calling-convention ownership + entry hook"; it does
   not switch the linking mode.** The link line is decided by whether the source file
   has `#[no_std]` — see [Bare metal and kernel development](/compiler/docs/osdev.html).
2. **Cross targets deliberately refuse to link.** Without `--no-link` they error out
   immediately, exit 1:

   ```text
   jhyy: refusing to link a cross target - this build's linker always emits a Windows .exe (via the bundled toolchain).
         Use --no-link, then link the .s with a toolchain that matches the target.
   ```

3. `--target` **does not switch between PE / ELF output** — the container format is
   decided by the host `ld` (ABI § 12.9).

### The full three-step cross-compilation

```bash
# 1. on Windows, emit the .s (a cross target must pass --no-link)
jhyy compile --target=amd64_sysv_freestanding --no-link prog.jhyy -o prog
#    ⇒ prog.s

# 2. on Linux, link it into a static ELF
gcc -nostdlib -static -T runtime/linux_elf/link.ld -o prog.elf \
    runtime/linux_elf/crt0.S prog.s

# 3. run it
./prog.elf
```

## 4. Three quirks you have to know

### 4.1 There is no `jhyy --version`

It never existed. Running it prints:

```text
jhyy: unknown option --version
(try `jhyy --help`)
```

Then it **exits with 1**. The version banner is on **the first line of `jhyy --help`**
— running `jhyy` with no arguments prints the same help, and the banner is on the first
line there too.

### 4.2 The command line accepts only one input file

Extra `.jhyy` arguments are **silently ignored** — no error, no warning. Measured:
`jhyy compile --no-link main.jhyy lib.jhyy -o multi` exits with 0, and the `multi.s`
it produces contains only the symbol of `main_jhyy`; not a single character of the
`lib_helper` that `lib.jhyy` defines.

To combine multiple files, use `import`: write `import lib;` in `main.jhyy`, and the
compiler compiles `lib.jhyy` in along the import graph.

### 4.3 Unrecognized options are rejected

```text
$ jhyy compile --foo main.jhyy
compile: unknown option --foo
(try `jhyy --help`)
```

Exit 1. It **does not** treat the flag as a file name and try to open it. `build` and
`run` each have their own prefix (`build: unknown option --foo` / `run: unknown
option --foo`).

## 5. Exit codes

| Situation | Exit code |
|---|---|
| `--help` / no arguments | 0 |
| `build` / `compile` succeeded | 0 |
| `run` succeeded | **the exit code of the program that ran** |
| Unknown option / unknown command / unknown target | 1 |
| Syntax error / semantic error | 1 (diagnostics go to stderr, with `file:line:col`) |
| The file cannot be opened | 1 |
| The cross target refuses to link | 1 |
| The link fails | 1 |

`jhyy run` passes the exit code of the program it ran through unchanged: the program
does `return 42` ⇒ `jhyy run` exits with 42.

Diagnostics look like this:

```text
bad.jhyy:1:33: error: unexpected token ';' in expression
bad.jhyy:1:29: error: expected ;, got return
parse errors
```

The wording of two other error paths:

```text
$ jhyy compile                        # no input file
usage: jhyy compile <file.jhyy> [-o output] [--no-link]

$ jhyy frobnicate x.jhyy             # unknown subcommand
jhyy: unknown command 'frobnicate'
(commands: compile / build / run / dump - try `jhyy --help`)
```

> **On "the exit codes match clang"**: neither the README, README.zh-CN, the CHANGELOG,
> nor the two specs **ever** make that statement. The measured semantics are exactly
> the table above — 0 on success, 1 on failure, and `run` additionally passes through
> the exit code of the program it ran.

> **Be careful reading exit codes in MSYS2 bash**: bash truncates the exit code to 8
> bits (`value & 0xFF`). For an exact exit code, use a harness or Python `subprocess`
> instead of reading `$?`.

## 6. Quick reference

```bash
# Compile and link into an exe
jhyy compile hello.jhyy

# Emit assembly only (a cross target has to take this route)
jhyy build hello.jhyy -o hello
jhyy compile --no-link --target=amd64_sysv_freestanding hello.jhyy -o hello

# Compile + link + run
jhyy run hello.jhyy

# Just look at the syntax tree
jhyy dump hello.jhyy

# The compiler's own help (the version banner is on the first line)
jhyy --help
```

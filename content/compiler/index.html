01 / 为什么是 JHYY

一门语言， 不是一个框架。

四条不让步的立场。每条都是一个小而具体的承诺，不是营销口号。

01 类型系统

静态，不是渐进。

类型在编译期检查。没有 any，没有隐式转换，没有逃生口。值一旦是 i32，在程序余下部分它就是 i32。 

type Point = struct { x: i32, y: i32 }
type Shape = enum { Circle(f32), Rect(f32, f32) }

const ORIGIN: Point = Point { x: 0, y: 0 }

fn area(s: Shape) -> f32 {
    match s {
        Circle(r) => 3.14 * r * r,
        Rect(w, h) => w * h,
    }
}
02 控制流

表达式，不是语句。

if、match 和块都返回值。函数的最后一个表达式就是返回值——不需要 return 关键字。 

fn dist_sq(a: Point, b: Point) -> i32 {
    let dx = a.x - b.x;
    let dy = a.y - b.y;
    dx * dx + dy * dy   // ← the return value
}
03 路线

一个能编译自己的编译器。

编译器用这门语言自己写。它编译自己，再让编译出来的自己编译自己；门要求各代产出的汇编逐字节相同。不动点是跑出来的，不是假设的——本地的门迭代 N=10 代。

03 / 一点语言的样子

四个文件， 整个语法。

hello.jhyy 
extern fn puts(s: *u8) -> i32;

fn main_jhyy() -> i32 {
    puts("Hello, world!");
    0
}
type Point = struct { x: i32, y: i32 }

fn dist_sq(a: Point, b: Point) -> i32 {
    let dx = a.x - b.x;
    let dy = a.y - b.y;
    dx * dx + dy * dy
}

fn main_jhyy() -> i32 {
    dist_sq(Point { x: 3, y: 4 }, Point { x: 0, y: 0 })
}
fn fib(n: i32) -> i32 {
    if n < 2 { n }
    else { fib(n - 1) + fib(n - 2) }
}

fn main_jhyy() -> i32 { fib(10) }
type Option = enum {
    Some(i32),
    None,
}

fn unwrap(o: Option) -> i32 {
    match o {
        Some(v) => v,
        None    => 0,
    }
}

fn main_jhyy() -> i32 {
    unwrap(Option::Some(99))
}

04 / 工具链

一个编译器， 和它周围的一切。

你拿到的可不只是 jhyy.exe。还有编辑器扩展、给 Claude Code 用的 MCP 服务，以及一套 arena 运行时——一门语言真要能用起来，缺的就是这四样。

编译器

jhyy compile foo.jhyy -o foo.exe 跑的是这条流水线：Lex → Parse → Sema → IL → 自研 amd64 发射器 → 本机代码。诊断带行号 + 列号。退出码与 clang 一致。没有 GC，热路径上没有 malloc——一次 arena_alloc，收尾一次 arena_free。

  • ·51 个 .jhyy 文件

05 / 现状与边界

什么能用， 什么不能用。

JHYY 是 pre-1.0 的项目：自举成立、回归全绿，但它还不是 C 或 Rust 的替代品。 这一屏把两边都写出来——只讲做到了什么，等于不讲。

✓ 已经成立

自举，且被验证过

编译器唯一的实现是 JHYY。它编译自己，再让编译出来的自己编译自己，门要求两代产出的汇编 逐字节相同。回归 {{regress_pass}} PASS / 0 FAIL / {{regress_skip}} SKIP（共 {{regress_total}} 条）， 产物级门 {{artifact_checks}} PASS / 0 FAIL，问题台账 {{workarounds_total}} 条里 ACTIVE = {{workarounds_active}}。

spec v{{spec_version}} · ABI v{{abi_version}} · binary format v{{binary_format_version}}
✗ 还没有

边界写在明面上

只有 amd64——没有 aarch64、没有 riscv、没有 wasm。宿主只有 Windows x64。 UEFI 入口路径尚未完工（ABI § 12.8）。没有 traits，没有 GC，借用检查目前只有最小的一层。 安装器和 MSI 未签名。裸机目标目前只支持裸机模式，链接仍需外部 ld。

裸机能力现状
→ 正在推

三个方向同时在跑

ARM 目标在 for-VEX 项目里——JHYY 直出 ARM 机器码，链官方 SDK。 操作系统的设计基线正在重整，当前只有一份 UEFI x64 引导 spike。 IDE把积木和文本接到同一棵 AST 上。

看家族另外三个项目
◆ 一条重要的区分

「逐字节相同」证明的是什么

自举闭环证明的是世代确定性——编译器精确地复现自己， 这是一条关于「确定性」的陈述，不是关于「语义正确性」的。语义正确性由回归套件单独覆盖。 这是经典的 trusting trust 缺口，两件事不能混为一谈。

06 / 看数字

没有 VM。 没有 JIT。没有运行时。

自研发射器在编译期直接产出 amd64 机器码。随附的运行时只有一个小 C 支撑库 （约 156 行），而且连它都可以不要——#[no_std] 下不链任何 C 运行时。 下面每个数字都注明了测量条件；基准比值的口径写在脚注里。

编译到 .s
 
本机实测（Windows 10 / i7-8550U / 2026-11-08，min of 8）。Lex → Parse → Sema → IL → 自研 amd64 发射器，产出汇编文本。
编译 + 链接
 
链接步骤由外部 gcc 驱动（现编现链 runtime + helpers），占掉绝大部分时间。只想看汇编用 jhyy build。

基准比值 vs gcc -O0
1.42× – 5.37×
9 个任务 / 4 条覆盖轴（整数与位运算、f64、堆、字节），min-of-15 墙钟。这是代码质量下限的比值，不是快慢的达标线——见下方说明。

关于这个比值：JHYY 目前没有优化器，产出的是接近 -O0 的代码， 所以拿 gcc -O0 作分母才是同一量纲的比较；gcc -O2 只作参考，不是通过/失败的标准。 比值已扣除测量底噪（进程创建 + 运行时启动；JHYY 的 shim 比裸 C 贵约 6 ms）。 其中 ack 与 nq 两题底噪占比超过 25%，口径不可靠，因此不报比值。 另外这套题测的是代码生成，不是标准库质量——标准库是另一根轴。 完整快照见仓库 bench/baseline/RESULTS-2026-11-04.md。

09 / 生态

站在可靠的工具之上。

JHYY 自己的编译器是自研的;但打包、分发和链接这几步,靠的是一批无聊但可靠的第三方工具。下面是其中几个。

GCC
编译器背后的编译器——Windows 上每次源码构建都由 mingw-w64-ucrt-x86_64-gcc 驱动。
↗
MSYS2
Windows 上的 POSIX shell + 包管理器。源码构建的入口——装一次，之后一直 make。
↗
mingw-w64
GCC 的 Windows 移植版。驱动链接步骤（as + ld）和 Windows 上每次源码构建。
↗
.NET 8 Desktop Runtime
承载安装器的首次运行向导 + UCPD 绕过助手。由 WiX chainer 自动捆绑。
↗
WiX Toolset 7.0
MSI 的构建工具。从 .wxs 到已签名、可交给 SCCM 的 .msi，一键完成。
